## 3. База даних

У кожній таблиці первинний ключ — `Id`, тип `int`, identity. Колонки й обмеження підтверджені запитами до `sys.tables`, `sys.columns`, `sys.key_constraints`, `sys.foreign_keys`, `sys.indexes`, `sys.check_constraints`.

- **Products**: обов’язкова назва до 50 символів; `Price decimal(18,2) NOT NULL`, ціна не від’ємна.
- **Customers**: обов’язкові ім’я/прізвище до 50 символів, необов’язкова адреса до 50, ціла знижка 0–100.
- **Supermarkets**: обов’язкова назва до 50 символів, необов’язкова адреса до 100.
- **Orders**: обов’язкові `CustomerId`, `SupermarketId`, дата `datetime2`.
- **OrderDetails**: обов’язкові `OrderId`, `ProductId`, ціла додатна кількість. Унікальний індекс `(OrderId, ProductId)` забороняє дублікати товару в одному замовленні.

Зв’язки та навігації:

| Головна сутність | Залежна сутність | FK | Навігації | Видалення у SQL Server |
|---|---|---|---|---|
| Customer | Orders | CustomerId | Customer.Orders ↔ Order.Customer | NO ACTION |
| Supermarket | Orders | SupermarketId | Supermarket.Orders ↔ Order.Supermarket | NO ACTION |
| Order | OrderDetails | OrderId | Order.OrderDetails ↔ OrderDetails.Order | CASCADE |
| Product | OrderDetails | ProductId | Product.OrderDetails ↔ OrderDetails.Product | NO ACTION |

Видалення замовлення видаляє його позиції. Товар, покупець або магазин, що використовуються, не видаляються: форма показує повідомлення. Зайвих каскадних шляхів немає.

Міграцію **InitialShoppingSchema** створено і застосовано. `__EFMigrationsHistory` містить `20261108151450_InitialShoppingSchema`. `EnsureCreated` не використовується. База не видалялася й не перестворювалася.

Початкове наповнення: **8 товарів, 6 покупців, 12 супермаркетів, 5 замовлень, 15 позицій**. Перший приклад має суму `25×2 + 40×3 + 60×1 = 230.00`. Імена Anna і Hanna дозволяють перевірити пошук `ann`.

Seed виконується лише для повністю порожньої БД. Якщо хоча б одна основна таблиця вже містить дані, наявні записи не змінюються й видалені демонстраційні записи не відновлюються. Серіалізована транзакція захищає початкове наповнення. Після перезапуску дублікати не з’явилися.

Сума замовлення обчислюється сервером: `Sum(Product.Price * Quantity)`, формат — два знаки після крапки. Відповідно до умови ціна береться з поточного каталогу; зміна ціни товару змінює також відображувану суму старих замовлень. Окремої історичної ціни схема не містить. Знижка зберігається як довідкова інформація й не змінює задану формулу.

## 4. Функціональність і відповідність 12 пунктам

У прикріпленому тексті немає самих університетських скриншотів або окремого нумерованого оригіналу завдання. Нижче зіставлено **12 явно перелічених користувацьких можливостей із розділу 4 наданої вимоги**. Відповідність невиданим скриншотам не підтверджується.

Позначення: PASS — реалізовано і перевірено зазначеним способом; PARTIAL — частково; FAIL — не виконано; NOT VERIFIED — перевірка не проводилася. Усі Razor-файли пройшли компіляцію. HTTP-перевірка підтверджує відповіді та HTML, але не замінює візуальну перевірку в браузері.

| Вимога | Статус | Файли | Перевірка |
|---|---|---|---|
| 1. Керування товарами | PASS | ProductsController, Models/Product, Views/Products | Реальний CRUD через HTTP і SQL; захист використаного товару |
| 2. Керування покупцями | PASS | CustomersController, Customer, Views/Customers, ListViewModels | CRUD; обидва напрями сортування прізвища/адреси; `ann` і порожній результат пошуку |
| 3. Керування супермаркетами | PASS | SupermarketsController, Supermarket, Views/Supermarkets | CRUD; 5/5/2 записів на сторінках; від’ємний і завеликий номер |
| 4. Реєстрація замовлень | PASS | OrdersController, Order, OrderCreateViewModel | POST з реальною вставкою; некоректні форми не створюють часткового замовлення |
| 5. Вибір супермаркету | PASS | Orders/_Form, OrdersController.ValidateAsync | Список назв; неіснуючий FK відхиляється |
| 6. Вибір покупця | PASS | Orders/_Form, OrdersController.ValidateAsync | Список повних імен; неіснуючий FK відхиляється |
| 7. Вибір кількох товарів | PASS | OrderCreateViewModel, Orders/_Form | Колекція Items[i], прапорці; замовлення з трьома товарами |
| 8. Перегляд цін товарів | PASS | Orders/_Form, Orders/_Summary, Products/Index | Ціни беруться з БД; підміна Price у POST не впливає на суму |
| 9. Введення кількості | PASS | OrderItemViewModel, OrderDetails, обидва контролери замовлень | Додатні значення; нуль, текст і дублікати відхиляються |
| 10. Збереження замовлення | PASS | OrdersController.Create/Edit, ShoppingContext | Транзакційний SaveChanges; зміни складу/кількості; дані зберігаються у SQL Server |
| 11. Перегляд усіх замовлень | PASS | OrdersController.Index, Orders/Index | HTTP 200; повні імена та назви завантажуються з Include |
| 12. Повні відомості про конкретне замовлення | PASS | OrdersController.Details, Orders/_Summary | Товари, ціни, кількість, суми 230.00/195.00/315.00/375.00; порожнє замовлення 0.00 |

Додаткові обов’язкові вимоги:

- **Повний OrderDetails CRUD**: `/OrderDetails/Index`, `/Create`, `/Details/{id}`, `/Edit/{id}`, `/Delete/{id}`. Посилання доступні зі сторінки замовлення. Перевірено додавання, зміну кількості й товару, видалення, дублікати та неправильний OrderId.
- **Редагування замовлення**: покупець, магазин, дата, додавання/вилучення товарів та кількість. Один SaveChanges забезпечує транзакційність; валідація відбувається до зміни сутностей.
- **Видалення замовлення**: сторінка підтвердження, каскад тільки його позицій; інші сутності залишаються.
- **Сортування/пошук**: IQueryable до ToListAsync, OrderBy/OrderByDescending і Contains; пошук зберігається в посиланнях сортування.
- **Пагінація**: OrderBy/ThenBy, Skip/Take, розмір 5; межі номера обмежуються; для порожньої таблиці код повертає сторінку 1/1 з неактивними кнопками. Саме порожню таблицю супермаркетів у робочій БД не створювали, тому цей крайовий випадок перевірено оглядом коду, без runtime-перевірки.
- **Захист**: DataAnnotations, ModelState, глобальний AutoValidateAntiforgeryToken, Bind у простому CRUD, окрема модель замовлення, перевірка FK і унікальності. Надіслані ціни не використовуються.
- **Навігація**: головна, товари, покупці, супермаркети, замовлення; Bootstrap 5, локальні статичні файли.

Загальний перелік: `/OrderDetails` або `/OrderDetails?orderId={id}`.

13. Для власного тестового замовлення видаліть усі позиції окремо. Відомості замовлення мають показувати повідомлення про відсутність товарів і **0.00 грн**. Через редагування знову додайте товар.

14. На `/Orders/Delete/{id}` перевірте підтвердження та видаліть власне тестове замовлення. У SQL Server його рядок і позиції мають зникнути; покупець, супермаркет і товари мають залишитися. Не використовуйте seed-замовлення, якщо плануєте повторно запускати перевірку початкової суми.

15. Створіть власний товар із впізнаваною назвою. Зупиніть процес Ctrl+C та повторіть `dotnet run --project ShoppingSystem`. Запис має залишитися, а початкові дані не повинні подвоїтися. Аналогічно можна залишити власне замовлення й перевірити його після перезапуску.

16. Відкрийте `/Orders/Details/2147483647`: очікується HTTP 404. Перевірте всі пункти меню, мобільне згортання меню, видимість помилок і таблиць. Цю візуальну частину потрібно виконати вручну.

Для повторення автоматизованої перевірки за запущеного застосунку:

```powershell
python .\ShoppingSystem\Verification\smoke.py
powershell -NoProfile -ExecutionPolicy Bypass -File .\ShoppingSystem\Verification\DatabaseChecks.ps1
# Перевірка перезапуску у другій консолі:
python .\ShoppingSystem\Verification\restart.py prepare
# Зупиніть і знову запустіть застосунок у першій консолі.
python .\ShoppingSystem\Verification\restart.py verify
```

Python потрібен лише для тестових скриптів, не для роботи MVC-застосунку. Скрипти змінюють БД через звичайні форми та прибирають власні записи; не запускайте їх одночасно з ручним редагуванням даних.
